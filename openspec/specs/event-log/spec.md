## Purpose

Надёжно хранить события на устройстве, переживать выключение зажигания и
выгружать данные без adb — через системный диалог сохранения на флешку.

## Requirements

### Requirement: Долговечная запись

Приложение MUST писать события в JSONL-файл, по одному событию на строку, и
MUST вызывать `fsync` для каждой записанной пачки. Приложение MUST NOT держать
единственную копию события только в памяти.

#### Scenario: Пропало питание

- **WHEN** питание магнитолы пропадает сразу после события
- **THEN** событие уже находится в файле на диске

#### Scenario: Файл за день

- **WHEN** наступают новые сутки
- **THEN** новые события пишутся в `events-YYYY-MM-DD.jsonl` за новую дату

### Requirement: Снимок диагностики

Приложение MUST сохранять JSON-снимок по кнопке и MUST сохранять снимок
автоматически при старте каждого трека. Снимок MUST содержать версию приложения,
модель устройства, версию Android, состояние доступа к уведомлениям,
состояние accessibility-доступа (системную настройку и фактическое
подключение сервиса), громкость выбранного источника, все аудиопотоки,
`isVolumeFixed`, `audioMode`, `isMusicActive`, аудиовыходы, все активные
сессии, последние уведомления с признаком `mediaLike`, состояние штатного
плеера с источником и сырыми текстами, состояние сервиса метаданных FYT,
состояние вендорного toolkit и список установленных пакетов Teyes/FYT/лаунчера.

#### Scenario: Первый трек в машине

- **WHEN** штатный плеер начал играть первый трек
- **THEN** рядом с журналом появляется снимок `snapshot-*-track_started.json`

#### Scenario: Громкость на Teyes

- **WHEN** пользователь делает снимок при громкости 4 на панели
- **THEN** снимок содержит `teyes.volume=4`, `teyes.max=43`, `teyes.source=mcu`,
  значения и максимумы всех аудиопотоков и `isVolumeFixed`, даже если
  `STREAM_MUSIC` показывает 25/25

#### Scenario: Штатный плеер без MediaSession

- **WHEN** штатный плеер не отдаёт MediaSession
- **THEN** снимок содержит `stockPlayer` с последним известным названием,
  источником, сырыми текстами accessibility и/или `RemoteViews`, а также
  список пакетов, по которым можно проверить имя плеера

#### Scenario: Неизвестное уведомление

- **WHEN** локальный плеер публикует уведомление без медиашаблона
- **THEN** оно попадает в снимок с `mediaLike = false`, но не создаёт событие
  `notification` в журнале

#### Scenario: Сервис метаданных FYT

- **WHEN** штатный плеер прислал `com.fyt.launcher.music`
- **THEN** снимок содержит `fytMetadataService.received=true`, пакет, набор
  ключей и время последнего обновления

#### Scenario: Accessibility включена, но сервис не подключён

- **WHEN** системная настройка accessibility включена, а сервис не подключён
- **THEN** снимок содержит `accessibilityEnabled=true` и
  `accessibilityConnected=false`

### Requirement: Экспорт ZIP

Приложение MUST экспортировать журнал, снимки и `manifest.json` в ZIP. Если
системный диалог сохранения доступен, приложение MUST использовать
`ACTION_CREATE_DOCUMENT`. Если обработчика нет, приложение MUST сохранить ZIP
в `Downloads/CarMusicMeter` через `MediaStore`, MUST NOT падать и MUST сообщить
путь к файлу. Экспорт MUST NOT зависеть от прав на запись по конкретному пути.

#### Scenario: Флешка только для чтения

- **WHEN** пользователь выбирает место на NTFS-флешке, доступной только для чтения
- **THEN** экспорт идёт через SAF и завершается успешно либо показывает понятную ошибку

#### Scenario: Нет системного диалога

- **WHEN** на магнитоле нажата кнопка «Экспорт логов», а обработчик
  `ACTION_CREATE_DOCUMENT` отсутствует
- **THEN** приложение не падает, сохраняет ZIP в `Downloads/CarMusicMeter`
  и показывает путь к файлу

#### Scenario: Телефон с SAF

- **WHEN** экспорт запускается на телефоне, где системный диалог есть
- **THEN** приложение использует обычный выбор файла и не пишет в Downloads
  без выбора пользователя

#### Scenario: Поделиться архивом

- **WHEN** ZIP сохранён через запасной путь
- **THEN** пользователь может открыть системное меню «Поделиться» для этого файла

### Requirement: Манифест выгрузки

Каждый ZIP MUST содержать `manifest.json` с версией формата (`schemaVersion`),
стабильным `deviceId`, номером выгрузки (`exportSeq`), временем выгрузки,
версией приложения, моделью устройства и списком файлов с путём, размером и
SHA-256. Манифест MUST содержать `range` (режим и границы выгрузки) и
`coverage` (фактические даты попавших файлов). Манифест MUST позволять
склеивать выгрузки без разбора содержимого журнала.

#### Scenario: Повторная выгрузка

- **WHEN** пользователь экспортирует журнал дважды
- **THEN** вторая выгрузка имеет больший `exportSeq` при том же `deviceId`,
  а файлы сопоставляются по пути и контрольной сумме

#### Scenario: Архив переименован

- **WHEN** ZIP переименовывают при переносе на ПК
- **THEN** по `manifest.json` видно устройство, номер и диапазон выгрузки

#### Scenario: Выгрузка за 30 дней

- **WHEN** пользователь выбирает пресет «30 дней»
- **THEN** в манифесте `range.mode` равен `days`, а `coverage` содержит
  фактические даты файлов, попавших в архив

### Requirement: Диапазон экспорта

Приложение MUST поддерживать выгрузку за всю историю (по умолчанию) и за
последние 90, 30 или 7 дней. Диапазон MUST применяться и к журналу, и к
снимкам. Если за выбранный период нет файлов, приложение MUST NOT создавать
ZIP и MUST показать понятное сообщение. Перед экспортом приложение MUST
показывать число файлов и оценку объёма.

#### Scenario: По умолчанию вся история

- **WHEN** пользователь запускает экспорт, не меняя период
- **THEN** в ZIP попадают все файлы, которые есть в хранилище

#### Scenario: Пресет 30 дней

- **WHEN** выбран период «30 дней»
- **THEN** в ZIP попадают только журнал и снимки за последние 30 дней

#### Scenario: Пустой период

- **WHEN** за выбранный период нет ни одного файла
- **THEN** ZIP не создаётся, пользователь видит сообщение «нет данных
  за период»

#### Scenario: Оценка перед экспортом

- **WHEN** пользователь открывает экспорт
- **THEN** приложение показывает число файлов и примерный объём

### Requirement: Состояние хранилища

Приложение MUST показывать, с какой даты хранится журнал, число файлов и
занятый объём, и MUST позволять настроить срок хранения и период экспорта.
Значения по умолчанию: хранение бессрочное, лимит 500 МБ, экспорт всей
истории.

#### Scenario: Экран данных

- **WHEN** пользователь открывает приложение
- **THEN** он видит дату начала журнала, число файлов и занятый объём

#### Scenario: Изменение срока хранения

- **WHEN** пользователь выбирает срок хранения
- **THEN** следующая чистка применяет новое значение и не удаляет текущий день

### Requirement: Диагностика запуска службы

Приложение MUST писать событие `service_started` с источником запуска:
`manual`, `boot`, `job`, `media_mounted`, `app_open`, `teyes_autostart`,
`accessibility`, `notification`, `fyt_service` или `watchdog`. Событие MUST
содержать `pid` и `newProcess`, чтобы отличить новый процесс от повторного
`onStartCommand`. Повторный запуск в том же процессе MUST NOT создавать второе
событие. Неудачная попытка запуска MUST писать `service_start_failed` с
источником и текстом ошибки. Штатная остановка службы MUST писать
`service_stopped` с причиной, `pid` и временем работы.

#### Scenario: Запуск после загрузки

- **WHEN** система прислала `BOOT_COMPLETED` и служба стартовала
- **THEN** в журнале есть `boot_received` и `service_started` с
  `source = boot`

#### Scenario: Запуск по отложенной задаче

- **WHEN** persisted JobScheduler сработал после загрузки
- **THEN** в журнале есть `service_started` с `source = job`

#### Scenario: Запуск при монтировании флешки

- **WHEN** система смонтировала USB-накопитель и служба стартовала
- **THEN** в журнале есть `service_started` с `source = media_mounted`

#### Scenario: Ручной запуск

- **WHEN** пользователь нажал «Запустить службу»
- **THEN** в журнале есть `service_started` с `source = manual`

#### Scenario: Запуск по уведомлению

- **WHEN** служба стартовала из обработчика медиа-уведомления
- **THEN** в журнале есть `service_started` с `source = notification`

#### Scenario: Запуск watchdog-задачей

- **WHEN** периодическая задача обнаружила, что служба не работает, и запустила её
- **THEN** в журнале есть `service_started` с `source = watchdog`

#### Scenario: Новый процесс

- **WHEN** служба стартовала после убийства процесса
- **THEN** `service_started` содержит новый `pid` и `newProcess=true`

#### Scenario: Штатная остановка

- **WHEN** пользователь остановил службу кнопкой
- **THEN** в журнале есть `service_stopped` с причиной `manual` и временем работы

### Requirement: Устойчивость к падениям

Приложение MUST сохранять стек необработанного исключения в файл рядом с
журналом и MUST писать событие `app_crash`.

#### Scenario: Приложение упало на магнитоле

- **WHEN** происходит необработанное исключение
- **THEN** в папке журнала появляется `crash-*.txt` со стеком

### Requirement: Очистка старых данных

Приложение MUST хранить журнал бессрочно по умолчанию и MUST соблюдать
настраиваемый срок хранения и защитный лимит объёма (по умолчанию 500 МБ).
При превышении лимита приложение MUST удалять самые старые завершённые дни,
кроме текущего. Приложение MUST оставлять не более 600 последних снимков и
50 crash-файлов. Возраст MUST определяться по дате из имени файла, а не по
`lastModified`. Чистка MUST фиксировать событие `retention_trimmed`.

#### Scenario: Достигнут лимит объёма

- **WHEN** суммарный объём журнала превышает настроенный лимит
- **THEN** удаляются самые старые завершённые дни, текущий день остаётся,
  а в журнал пишется `retention_trimmed`

#### Scenario: Бессрочное хранение

- **WHEN** срок хранения равен «бессрочно» и лимит объёма не достигнут
- **THEN** старые файлы журнала не удаляются

#### Scenario: Снимки и crash-файлы

- **WHEN** снимков больше 600 или crash-файлов больше 50
- **THEN** удаляются самые старые из них, журнал не затрагивается

#### Scenario: Сбитые часы магнитолы

- **WHEN** `lastModified` файла не совпадает с датой в его имени
- **THEN** срок хранения считается по дате из имени

#### Scenario: Журнал за год

- **WHEN** приложение запускается после долгого перерыва
- **THEN** старые файлы удаляются по действующей политике, свежие остаются

### Requirement: Диагностика источников штатного плеера

Приложение MUST писать событие `stock_player_text` при изменении текста,
полученного от штатного плеера, и MUST указывать источник
(`fyt_service`, `fyt_broadcast`, `accessibility`, `notification`), пакет,
название, исполнителя и сырые тексты. Приложение MUST NOT писать это событие
на каждом тике, если текст не изменился. На устройстве Teyes/FYT приложение
MUST писать `teyes_toolkit` при первом подключении, смене доступности или
ошибке вендорного сервиса.

#### Scenario: Accessibility впервые увидел трек

- **WHEN** accessibility-сервис получил новый набор текстов штатного плеера
- **THEN** в журнале появляется `stock_player_text` с `source=accessibility`
  и сырыми текстами

#### Scenario: Broadcast обновил тот же трек

- **WHEN** broadcast присылает то же название и исполнителя повторно
- **THEN** повторное событие `stock_player_text` не пишется

#### Scenario: Сервис метаданных FYT обновил трек

- **WHEN** `com.fyt.launcher.music` прислал новый `title` или `play_path`
- **THEN** в журнале появляется `stock_player_text` с `source=fyt_service`

#### Scenario: MCU-сервис недоступен

- **WHEN** приложение не смогло подключиться к `com.syu.ms`
- **THEN** в журнале появляется `teyes_toolkit` с `available=false` и
  причиной, а служба продолжает работать

### Requirement: Диагностика UI штатного плеера

Приложение MUST сохранять диагностику UI штатного плеера в снимке и в событии
`stock_player_ui` при изменении состояния или по кнопке «Снять срез». Диагностика
MUST содержать все видимые тексты без фильтра, для каждого узла — `className`,
`viewIdResourceName`, `text`, `contentDescription`, `rangeInfo`, а также список
окон с пакетом, заголовком, признаками `active`/`focused`. Приложение MUST
ограничивать число узлов и MUST NOT писать событие на каждом тике без изменений.

#### Scenario: Плеер в split-screen

- **WHEN** пользователь делает снимок, когда плеер виден рядом с навигатором
- **THEN** снимок содержит окно `com.syu.music`, его узлы и `rangeInfo` прогресса

#### Scenario: Переходный экран

- **WHEN** плеер открылся и первое чтение вернуло заголовок папки
- **THEN** `stock_player_ui` содержит все тексты и признак, что парсер отклонил состояние

#### Scenario: Повторный тик

- **WHEN** UI плеера не изменился с прошлого тика
- **THEN** повторное событие `stock_player_ui` не пишется

### Requirement: Диагностика потери источника

Приложение MUST писать событие `capture_gap` только при реальной потере
источника штатного плеера, когда ни один источник не даёт свежих метаданных.
Событие MUST содержать `active`, причину, последний известный трек (если он
есть; иначе `null`), `isMusicActive` и список видимых окон. Если accessibility
выключена или не подключена, а музыка активна и источника нет, служба
наблюдения MUST писать `capture_gap` с причиной `no_source`. Если окно плеера
скрыто, но `fyt_service` или другой источник активен, приложение MUST NOT
писать `capture_gap`. Событие MUST писаться один раз на границу разрыва и MUST
NOT заменять `track_ended` или `track_progress`.

#### Scenario: Плеер ушёл в фон

- **WHEN** окно плеера перестало быть видимым, музыка играет, а других источников нет
- **THEN** появляется `capture_gap` с `active = true` и последним треком

#### Scenario: Источник ещё не был известен

- **WHEN** музыка играет, источника нет, и последний трек ещё не записан
- **THEN** появляется `capture_gap` с `active = true`, `lastTitle = null` и
  `lastArtist = null`

#### Scenario: Accessibility выключена

- **WHEN** музыка играет, accessibility выключена или не подключена, а других источников нет
- **THEN** появляется `capture_gap` с `active = true` и `reason = no_source`

#### Scenario: Окно скрыто, но источник активен

- **WHEN** окно плеера скрыто, а `fyt_service` продолжает отдавать свежие метаданные
- **THEN** `capture_gap` не пишется, потому что источник не потерян

#### Scenario: Плеер вернулся

- **WHEN** источник снова стал доступен
- **THEN** появляется `capture_gap` с `active = false` и причиной восстановления

### Requirement: Согласованность границ трека

`track_ended` одного прослушивания MUST содержать тот же `mediaId` и
`durationMs`, что и его `track_started`, если источник отдал их при старте.
Переходный intent со следующим `play_path` MUST NOT подменять поля текущего
трека. Если длительность неизвестна, `durationMs` MUST оставаться `null`.

#### Scenario: Переходный intent со следующим путём

- **WHEN** приходит intent со старым `title`, новым `play_path` и без `play_total`
- **THEN** `track_ended` текущего трека содержит его прежние `mediaId` и `durationMs`, а не поля следующего трека

#### Scenario: Длительность неизвестна

- **WHEN** источник не отдал `durationMs` ни при старте, ни при окончании
- **THEN** `track_ended` содержит `durationMs = null`, а не длительность другого трека

#### Scenario: Пауза

- **WHEN** приходит `play_state=false` для текущего трека
- **THEN** `track_ended` не пишется, а трек остаётся текущим в состоянии `PAUSED`

### Requirement: Ограничение playedMs на технических окончаниях

При окончаниях `session_lost`, `service_stopped`, `stopped` и `unknown`
приложение MUST писать в `track_ended` `playedMs`, ограниченный `durationMs`,
если длительность известна, и MUST сохранять исходное накопленное значение в
`rawPlayedMs`. Если длительность неизвестна, `playedMs` MUST оставаться
оценочным, а `rawPlayedMs` MUST совпадать с ним. `completed` и `skipped` MUST
NOT использовать `rawPlayedMs`.

#### Scenario: Потеря источника после длинного трека

- **WHEN** трек `Рассвет` закрылся с `session_lost`, `durationMs=185000` и
  накопленным временем 205669 мс
- **THEN** `track_ended` содержит `playedMs=185000` и `rawPlayedMs=205669`

#### Scenario: Длительность неизвестна

- **WHEN** трек закрылся с `session_lost`, а `durationMs=null`
- **THEN** `playedMs` и `rawPlayedMs` равны накопленному времени

#### Scenario: Обычное завершение

- **WHEN** трек закрылся как `completed` и накопленное время меньше длительности
- **THEN** `playedMs` и `rawPlayedMs` равны, ограничение не применяется

### Requirement: Событие media_button

Приложение MUST писать событие `media_button` на каждый полученный
`ACTION_MEDIA_BUTTON` с полями `keyCode`, `action` (`down`/`up`),
`eventTime`, `repeatCount`, `sourcePackage` (если известен), `trackKey`,
`title` и `artist` текущего трека (если он известен). Событие MUST NOT
заменять `track_started`/`track_ended` и MUST NOT влиять на статистику
прослушиваний.

#### Scenario: Следующий трек

- **WHEN** пришёл `KEYCODE_MEDIA_NEXT` с действием `down`
- **THEN** событие содержит `keyCode=87`, `action=down` и текущий `trackKey`

#### Scenario: Нет текущего трека

- **WHEN** нажатие пришло, пока трек неизвестен
- **THEN** событие содержит `trackKey=null`, `title=null`, `artist=null`

#### Scenario: Down и Up

- **WHEN** пришли оба действия одного нажатия
- **THEN** в журнале есть два события `media_button` с разными `action`

### Requirement: Диагностика сервиса метаданных FYT

Приложение MUST писать событие `fyt_metadata_service` при первом получении
метаданных `com.fyt.launcher.music` и при изменении набора extras. Событие MUST
содержать `received=true`, `package`, `keys`, `title`, `artist` и `playing`.
Если intent не получен, приложение MUST NOT писать `received=false` на каждом
тике: отсутствие события означает, что текущий пакет не получает данные.

#### Scenario: Первый intent

- **WHEN** сервис впервые получил `com.fyt.launcher.music`
- **THEN** в журнале появляется `fyt_metadata_service` с `received=true` и
  списком ключей

#### Scenario: Новый набор extras

- **WHEN** в следующем intent появился ключ, которого не было раньше
- **THEN** появляется новое событие `fyt_metadata_service` с обновлённым `keys`

#### Scenario: Пакет не получает данные

- **WHEN** за поездку не пришло ни одного `com.fyt.launcher.music`
- **THEN** событий `fyt_metadata_service` нет, а остальные источники
  продолжают работать

### Requirement: Статус подключения accessibility

Снимок диагностики MUST содержать `accessibilityEnabled` (значение системной
настройки) и `accessibilityConnected` (фактическое подключение сервиса).
Приложение MUST писать `accessibility_state_changed` при изменении настройки,
`accessibility_connected` при подключении сервиса и
`accessibility_disconnected` при отключении. Отключение MUST NOT ронять службу.

#### Scenario: Настройка включена, сервис не подключён

- **WHEN** системная настройка accessibility включена, а сервис не подключён
- **THEN** снимок содержит `accessibilityEnabled=true` и
  `accessibilityConnected=false`

#### Scenario: Сервис подключился

- **WHEN** accessibility-сервис подключился
- **THEN** в журнале появляется `accessibility_connected`

#### Scenario: Система выключила accessibility

- **WHEN** системная настройка сменилась на выключенную
- **THEN** в журнале появляется `accessibility_state_changed` с `enabled=false`

#### Scenario: Сервис отключился

- **WHEN** accessibility-сервис отключился, а служба продолжает работать
- **THEN** в журнале появляется `accessibility_disconnected`, служба не падает

### Requirement: Периодический watchdog службы

Приложение MUST планировать периодическую задачу JobScheduler, которая при
включённом автозапуске проверяет, работает ли `MediaWatchService`, и запускает
её с источником `watchdog`, если служба не работает. Задача MUST NOT запускать
вторую копию службы, MUST NOT мешать работе и MUST логировать только факт
запуска или ошибку.

#### Scenario: Служба убита

- **WHEN** watchdog сработал, а служба не работает
- **THEN** появляется `service_started` с `source=watchdog`

#### Scenario: Служба работает

- **WHEN** watchdog сработал, а служба уже работает
- **THEN** новая служба не запускается и событие не пишется

#### Scenario: Автозапуск выключен

- **WHEN** автозапуск выключен
- **THEN** watchdog ничего не запускает

### Requirement: Статус подключения notification listener

Снимок диагностики MUST содержать отдельное поле `notificationListenerConnected`,
отражающее фактическое подключение `NotificationListenerService`, а не только
выданное разрешение. Приложение MUST обновлять статус при подключении и
отключении listener.

#### Scenario: Разрешение есть, listener не подключён

- **WHEN** доступ к уведомлениям выдан, но listener не подключён
- **THEN** снимок содержит `notificationAccess = true` и `notificationListenerConnected = false`

#### Scenario: Listener подключён

- **WHEN** `NotificationListenerService` подключился
- **THEN** снимок содержит `notificationListenerConnected = true`

### Requirement: Устойчивость к ошибкам записи

Ошибка записи пачки событий MUST NOT останавливать цикл наблюдения. Приложение
MUST повторять запись с задержкой, MUST сохранять событие либо сообщать о его
потере в диагностике, и MUST NOT оставлять службу в состоянии «работает» без
предупреждения. После восстановления записи приложение MUST продолжить писать
события.

#### Scenario: Диск заполнен

- **WHEN** при записи пачки возникла ошибка ввода-вывода
- **THEN** служба продолжает опрос, на экране и в уведомлении видна ошибка,
  а после освобождения места запись возобновляется

#### Scenario: Ошибка не маскируется

- **WHEN** запись недоступна дольше одного тика
- **THEN** диагностика показывает этап, текст ошибки и число неудачных попыток

### Requirement: Контрольная точка текущего прослушивания

Пока трек активен, приложение MUST писать событие `track_progress` не реже
одного раза в 60 секунд во время `PLAYING` и при переходе в `PAUSED` или
`STOPPED`. Событие MUST содержать `trackKey`, `positionMs`, `playedMs`,
`volume`, `phase` и `ts`. Последняя контрольная точка MUST позволять
восстановить прослушанное время открытого трека при выгрузке.

#### Scenario: Питание пропало в середине трека

- **WHEN** зажигание выключилось между двумя контрольными точками
- **THEN** в журнале остаётся последний `track_progress`, и отчёт использует его
  `playedMs` для открытого прослушивания

#### Scenario: Пауза

- **WHEN** трек перешёл в `PAUSED`
- **THEN** перед паузой или в момент перехода пишется `track_progress` с
  актуальными `playedMs` и `positionMs`

### Requirement: Однократная финализация при остановке

После начала остановки службы приложение MUST прекратить создание новых
`track_started` и MUST записать не более одного `track_ended` для текущего
трека. Финализация MUST выполняться после того, как цикл перестал обрабатывать
тики.

#### Scenario: Остановка во время тика

- **WHEN** служба останавливается, пока цикл обрабатывает очередной тик
- **THEN** в журнале появляется ровно один `track_ended`, а новых
  `track_started` после остановки нет

#### Scenario: Повторная остановка

- **WHEN** остановка службы запрошена повторно
- **THEN** повторный `track_ended` не пишется
