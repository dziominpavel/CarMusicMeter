# Design

## Context

См. `proposal.md` — Why. Технические ограничения, которые формируют подход:

- Всё решается в одном модуле `:app`; `ListeningTracker` — чистая логика без
  Android и покрыта JVM-тестами, поэтому всё, что можно, стоит держать там.
- Журнал append-only JSONL с fsync; буферы в памяти теряются при выключении
  зажигания. Значит, любое состояние, которое нужно после перезапуска, должно
  быть либо на диске, либо выводимо из журнала.
- На магнитоле нет adb: проверить можно только выгрузкой ZIP и разбором на ПК.
- Источник громкости MCU обновляется **только колбэком** вендора; синхронный
  `getInt`/`transact(2)` почти всегда возвращает `null` (проверено на ZIP
  2026-11-04: 15 переключений источника за 17 минут при живом сервисе).

## Goals / Non-Goals

**Goals:**

- Убрать шум, который делает месяц сбора дорогим и нечитаемым, не потеряв
  диагностику, нужную для отладки парсера.
- Сделать так, чтобы «сделал громче» измерялось на одной шкале и не пропадало
  из-за таймера.
- Сделать журнал самодостаточным: по нему должно быть видно и порядок событий,
  и незакрытые прослушивания, без внешнего состояния.
- Держать формат совместимым: новые поля только добавляются, старые ZIP читаются
  как раньше.

**Non-Goals:**

- Не меняем политику хранения, лимиты и пресеты экспорта.
- Не добавляем перехват подрулевых кнопок через вендорный сервис.
- Не меняем семантику `skip_rate`/`completion` и пороги кандидатов на удаление.
- Не пытаемся «починить» уже записанные события 2023 года — только корректно
  показать их в отчёте.

## Decisions

### 1. Подпись окна плеера для throttle

`UiLogThrottle` сравнивает сигнатуру, которая сейчас включает тикающую позицию.
Считаем сигнатуру по смысловым полям: пакет и заголовок окна, набор видимых окон,
`accepted`, `rejectReason`, `title`, `artist`, `durationMs`, число узлов и
множество `className+viewId` без `text`. Строки вида `mm:ss`/`hh:mm:ss` и
`rangeInfo.current` из подписи исключаются.

Тело события при записи остаётся полным (все `nodes`, `allTexts`, `rangeInfo`) —
теряется только частота, а не информация. Ручной снимок по-прежнему отдаёт
полный дамп в любой момент.

*Альтернативы:* (а) писать `stock_player_ui` только при смене трека — теряем
переходные экраны и диагностику парсера; (б) оставить как есть и чистить на ПК —
данные уже записаны с шумом, fsync каждые 2–3 секунды на магнитоле остаётся.

*Дополнительно:* раз в 5 минут писать «якорное» событие, даже если ничего не
изменилось, чтобы в журнале было видно, что окно плеера было видно. Это десяток
событий за поездку вместо семисот.

### 2. Подпись текста штатного плеера

`stock_player_text` дедуплицируется по `(package, source, title, artist, album,
нормализованный набор сырых строк)`, где из сырых строк выброшены временные
токены (`^\d{1,2}:\d{2}(:\d{2})?$`). Для accessibility это обязательное условие:
в `rawTexts` плеера всегда есть текущее время и время трека.

### 3. Свежесть громкости MCU

Убираем таймер `STALE_MS = 60 с` как причину отката. Значение MCU считается
действительным, пока сервис подключён, `volume != null` и binder жив. `refresh()`
остаётся, но его `null` больше не признак устаревания — это норма для этого
сервиса. Откат на `AudioManager` происходит только при смерти binder, ошибке
`bindService` или отсутствии модуля `sound`, с прежними причинами
`mcu_unavailable`/`mcu_error`.

*Ключевой trade-off:* мы предпочитаем возможную устаревшую громкость гарантированно
мусорной (`25/25` из `STREAM_MUSIC`). Громкость панели не меняется сама, и каждое
её изменение приходит колбэком, поэтому «последнее прочитанное» — корректное
значение с точностью до пропущенного колбэка.

*Альтернативы:* (а) поднять `STALE_MS` до суток — тот же эффект, но скрытый;
(б) чинить синхронное чтение вендорного API — неизвестный код возврата, нет adb
для проверки; (в) писать оба источника в каждом событии — раздувает формат и не
решает `volume_delta`.

### 4. Финализация открытого прослушивания

Сохраняем «открытое прослушивание» в `Prefs` синхронным `commit()` при каждой
контрольной точке (раз в 60 с, на паузе/остановке и на старте трека): `trackKey`,
`startedAtWallMs`, `playedMs`, `lastTsWall`, `bootId`. При старте службы, если
запись есть и её `trackKey` не закрыт, пишем ровно один
`track_ended(session_lost)` с `playedMs` из сохранения, затем стираем запись.
Проверка «не закрыт» — по `bootId`: если сохранённый `bootId` совпадает с текущим,
значит это тот же процесс и закрывать нечего.

*Альтернатива:* читать хвост JSONL на старте и искать непарный `track_started`.
Отклонено: старт трека может лежать в файле другого дня (сбитые часы) или за
пределами хвоста, а разбор требует второй реализации логики пар.

*Риск двойного закрытия* при наложении процессов (установка APK) снимается на ПК:
дубль `track_ended` для одной пары `trackKey + startedAt` отчётом отбрасывается.

### 5. Конверт события

`bootId` и `monoMs` добавляются в одном месте — при сериализации в `EventLog`,
а не в каждом построителе события. `bootId` — короткий идентификатор процесса,
генерируется в `Application.onCreate`; `monoMs` — `SystemClock.elapsedRealtime()`
на момент записи пачки. События без этих полей (старые ZIP) читаются как раньше.

Поправку часов не храним отдельным полем: `clock_changed` уже содержит `wallDelta`,
`monoDelta` и `driftMs`, а пара `(bootId, monoMs)` делает преобразование
восстановимым. Отчёт строит по `clock_changed` кусочно-линейное соответствие
`monoMs → ts` и применяет его к событиям того же `bootId`. Старые ZIP без
конверта обрабатываются по `ts`.

### 6. Дельта громкости в отчёте

`volume_delta` берётся из `volumeStats.mcu` (`end - start`). Нет сегмента —
`None`, а не `0`; в таблице печатается `-`, в агрегатах участвуют только
известные значения, и отдельно выводится доля прослушиваний без MCU-сегмента
(маркер неполных данных). Верхнеуровневые поля остаются для отладки.

## Risks / Trade-offs

- [Подпись окна слишком грубая, потеряем диагностику переходных экранов] →
  `rejectReason` и `accepted` входят в подпись; ручной снимок даёт полный дамп;
  «якорное» событие раз в 5 минут.
- [Пропущенный колбэк громкости даёт устаревшее значение] → периодический
  `refresh()` остаётся; при живом binder'е он обновляет значение, когда API
  отвечает.
- [Запись в `Prefs` на каждом чекпоинте — лишний I/O] → синхронный `commit()`
  раз в 60 с, вне главного потока, на порядок дешевле fsync журнала.
- [Двойное закрытие прослушивания при перекрытии процессов] → отчёт отбрасывает
  повторную пару `trackKey + startedAt`.
- [Поправка часов не восстановится, если `clock_changed` не попал в выгрузку] →
  отчёт падает обратно на `ts` и помечает день как подозрительный.
- [Увеличение размера события на ~40 байт] → около 30 КБ в месяц, на фоне
  сокращения диагностики на два порядка.

## Migration Plan

1. Собрать `debug` через `build-apk.bat`, поставить с флешки на магнитолу.
2. Одна поездка утром и вечером; выгрузить ZIP **после** поездки, а не в середине
   (текущая выгрузка 2026-11-04 обрезала вечер на 19:23).
3. Проверить на ПК: `stock_player_ui` — единицы на трек; `volume_delta` не
   теряет подъёмы; ни одного незакрытого прослушивания после перезагрузки;
   `clock_changed` не создаёт отдельный день.
4. Откат: предыдущий APK лежит в `dist\archive\`, формат журнала совместим в обе
   стороны, чистить данные не нужно.
