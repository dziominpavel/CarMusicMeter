# Design

## Context

См. `proposal.md` — Why. Ниже только то, что влияет на подход.

- Магнитола Teyes CC3 после полной потери питания стартует с часами
  `2023-05-10 11:13:59` и получает реальное время по NTP через ~40–45 секунд.
  Приложение автозапускается раньше, поэтому первые события каждого холодного
  старта всегда попадают в «непроверенное» окно.
- adb на магнитоле нет: ни `logcat`, ни `shell`. Всё, что нужно для разбора,
  должно попадать в ZIP.
- Журнал append-only с fsync на пачку. Держать события только в памяти нельзя.
- `scripts/report.py` уже умеет `clock_jumps`, `corrected_ts` и `order_events`
  по `bootId`/`monoMs` — эта часть работает и переиспользуется.
- `EventLog.exportTo` уже читает каждый файл целиком (SHA-256 считается по ходу
  копирования) — там же бесплатно можно собрать статистику по файлу.
- Наблюдение: `playedMs > durationMs` на `completed` — не баг, а сумма
  просуммированного времени после перемоток назад; отчёт уже ограничивает
  `heard` и `completion` единицей.

## Goals / Non-Goals

**Goals:**

- Ни одно событие не пишется в файл с датой, которая не подтверждена.
- Отчёт и `coverage` никогда не показывают 2023 год для данных 2026-го.
- Одно непрерывное воспроизведение даёт ровно одно прослушивание, даже если
  процесс заменили в середине.
- `mediaId`/`durationMs`/`album` прослушивания неизменны от старта до конца.

**Non-Goals:**

- Чинить RTC магнитолы или настраивать NTP.
- Переразбирать старые журналы (`2000100027`, `2000100031`): только предупреждение.
- Менять `minSdk`, разрешения и добавлять сеть.
- Менять версию приложения: сборка тестовая, `debug`.

## Decisions

### D1. Признак недостоверных часов — два условия

`clockVerified = false`, если `now < buildDateMs` (часы раньше сборки APK —
физически невозможно) **или** `now < lastVerifiedWallMs - 1h` (время откатилось
относительно прошлой подтверждённой сессии). `lastVerifiedWallMs` хранится в
`Prefs` и обновляется на каждом проверенном тике (не чаще раза в минуту).

Почему не сверка с файлом-меткой на диске: `BuildConfig` уже содержит дату
сборки (`04.11.2026 22:56` видна в снимках), а прошлое значение нужно только
для откатов в «плюс». Двух условий хватает на наблюдаемый случай (2023 год) и
на ручную правку часов назад.

### D2. Непроверенные события — в отдельный файл

Пока `clockVerified = false`, `EventLog` пишет в `events-unverified.jsonl`
(без даты в имени). После первого подтверждённого тика — в файл по дате.

Почему не файл по «дате последнего подтверждённого времени»: при стоянке в
несколько дней дата всё равно врёт, и отличить такие события можно только по
полю. Почему не буфер в памяти: нарушает правило «событие либо на диске с
fsync, либо его нет».

Следствие: `StorageDates.logDate()` возвращает `null`, поэтому
`RetentionPlanner` обязан считать недатированный журнал текущим (не удалять), а
`ExportPlanner` — всегда включать его в выгрузку.

### D3. Поправка — `shiftMs` в `clock_changed`

`clock_changed.shiftMs = wallDelta - monoDelta` — величина, которую надо
прибавить к `ts` событий, записанных **до** скачка в этом `bootId`. Отчёт
сейчас выводит её сам, но журнал должен быть самодостаточным: если `monoDelta`
не попадёт в событие, восстановление всё равно возможно.

Почему не `clockShiftMs` в каждом событии: раздувает журнал, а восстановление
по `bootId`+`monoMs` уже реализовано.

### D4. `clockVerified` — в конверт события

Поле живёт рядом с `bootId`/`monoMs` в `Json.eventToJson`, значение — состояние
на момент записи. Плюс ~25 байт на строку.

### D5. Манифест версии 2: `logs[]` и `coverage` по событиям

Во время копирования файла в ZIP `EventLog.exportTo` дополнительно считает:
число строк-событий, `fromMs`/`toMs` по фактическому времени, число событий с
`clockVerified = false`, наличие `clock_changed`. Разбор лёгкий (поиск
`"ts":`, `"clockVerified"`, сравнение `type`), полный `JSONObject` не нужен.

`coverage` считается по `fromMs`/`toMs` этих файлов, а не по датам в именах.
`schemaVersion` = 2; отчёт читает и 1, и 2.

Почему не отдельный индекс на диске: на магнитоле каждая запись в цикле
стоит дорого, а экспорт — ручное действие.

### D6. Поля прослушивания только дополняются

`preserveSameTrackFields` превращается в «fill-only»: `durationMs`, `mediaId`,
`album` берутся из нового snapshot только если в текущем они `null`.
Правило не зависит от `play_state` и `play_total`, поэтому переходный intent с
длительностью следующего трека больше не протекает. Значения `0` для
`durationMs` считаются неизвестными и заменяются.

Почему не сверять `play_path` с ожидаемым: путь не входит в идентичность трека
по спеке, и сравнение даст ложные закрытия.

### D7. Восстановленное прослушивание продолжается, а не закрывается

`closeRestoredPlay` больше не решает сразу: сохранённое прослушивание
запоминается как `pendingRestored`, и решение принимается на первом тике:

- текущий snapshot имеет тот же `trackKey` → `ListeningTracker.adoptRestored`
  создаёт `Active` с `startedAt` и `playedMs` из сохранённого состояния,
  событий не пишется;
- snapshot другого трека → прежнее прослушивание закрывается одним
  `track_ended(session_lost, restored = true)`, затем идёт обычный тик;
- snapshot нет и прошло больше 10 секунд → закрывается так же, как сейчас.

Почему не «всегда продолжать»: приписывать новому треку чужое `startedAt`
нельзя. Почему не «всегда закрывать»: тогда обновление APK во время трека
даёт лишнее прослушивание на 0 мс и режет одно воспроизведение на два.

### D8. Отчёт: восстановление дат в три шага

1. `clockVerified == false` и есть `clock_changed` в том же `bootId` выше по
   `monoMs` → дата считается по поправке (уже реализовано в `corrected_ts`).
2. `clockVerified == false` и поправить нечем → событие не создаёт поездку,
   попадает в счётчик «дата не подтверждена».
3. Выгрузка `schemaVersion` 1 без `clockVerified` → fallback: событие без
   конверта, чей `ts` раньше `exportedAt` больше чем на 365 дней, тоже
   считается неподтверждённым. Это единственный способ не показывать 2023 год
   для уже собранного архива; в отчёте fallback помечается как эвристика.

### D9. Диагностика часов

В снимок добавляется блок `clock` (`verified`, `lastVerifiedAt`,
`shiftMs`, `unverifiedEvents`), на экране диагностики и на пульте — строка
предупреждения, пока часы не подтверждены.

## Risks / Trade-offs

- [Файл без даты в имени ломает срок хранения] → `RetentionPlanner` трактует
  `events-unverified.jsonl` как текущий день и никогда не удаляет его по сроку.
- [Часы могут откатиться к дате после сборки] → ловится условием
  `now < lastVerifiedWallMs - 1h` на следующем старте.
- [Эвристика 365 дней для старых ZIP может пометить реальный журнал] →
  применяется только при отсутствии поля `clockVerified` и помечается в отчёте.
- [«Залипание» неверной длительности после fill-only] → `0` и `null`
  считаются неизвестными и заменяются; на 11-05 все длительности приходили
  корректными на старте трека.
- [Рост журнала на `clockVerified`] → ~25 байт на событие, на реальных объёмах
  (сотни событий в день) незначимо.
- [Новый путь `adoptRestored` в трекере] → обязательные JVM-тесты на
  продолжение, на другой трек и на отсутствие snapshot.
- [Сборка не проверена в машине до выезда] → тестовая `debug`-сборка, проверка
  сценария «долгая стоянка → холодный старт» отдельным пунктом чек-листа.

## Migration Plan

1. `manifest.schemaVersion` 1 → 2; `report.py` читает обе версии.
2. Уже собранный архив `CarMusicMeter-b9aeedbf-all-20261105-1841.zip`
   пересобирать не нужно: fallback из D8 не даст ему создать поездку в 2023.
3. `events-2023-05-10.jsonl`, лежащий на магнитоле, остаётся как есть; новых
   событий в нём не появляется. Приложение само журнал не удаляет.
4. Откат: установка прежнего APK. Новый файл `events-unverified.jsonl` старый
   код не создаёт, а при наличии прочитает как обычный журнал — данные не
   теряются.
