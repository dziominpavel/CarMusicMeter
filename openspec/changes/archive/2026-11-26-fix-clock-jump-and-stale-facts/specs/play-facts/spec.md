# Spec Delta

## ADDED Requirements

### Requirement: Достоверность времени прослушивания

При скачке настенных часов приложение MUST переносить поправку `shiftMs` на
старт активного прослушивания, чтобы `startedAt` и `raiseMs`/`dropMs` оставались
в реальном времени, а файл дня выбирался по исправленной дате. `clockVerified`
MUST определяться по времени старта, а не по моменту закрытия. Факт, у которого
`startedAt` позже `endedAt` или раньше его больше чем на сутки, MUST читаться
как `clockVerified=false` и MUST NOT расширять период отчёта.

#### Scenario: Скачок часов во время трека

- **WHEN** трек начался при часах магнитолы, показывающих 2023 год, а через
  минуту пришло реальное время
- **THEN** факт получает реальный `startedAt` и `clockVerified=true`,
  `raiseMs`/`dropMs` считаются от исправленного старта, а файл дня выбирается
  по реальной дате

#### Scenario: Трек начался после исправления часов

- **WHEN** часы исправлены до старта трека
- **THEN** поправка к `startedAt` не применяется

#### Scenario: Уже записанный факт с датой из 2023 года

- **WHEN** отчёт читает факт, у которого `startedAt` отстоит от `endedAt`
  больше чем на сутки
- **THEN** факт помечается `clockVerified=false`, показывается как «дата не
  подтверждена» и не расширяет период

#### Scenario: Обычное прослушивание

- **WHEN** `startedAt` и `endedAt` одного прослушивания отличаются меньше чем
  на сутки
- **THEN** признак `clockVerified` факта не меняется

## MODIFIED Requirements

### Requirement: Разбор истории

Для дней без live-фактов приложение MUST строить факты из `events-*.jsonl`
без действий пользователя. Разбор MUST применять поправку `clock_changed`,
порядок `bootId`/`monoMs` и правила `endReason`/`playedMs`. Результат MUST
кэшироваться по дням и инвалидироваться при смене версии builder'а или
источника. Кэш MUST быть безопасно удаляемым. Открытым MUST оставаться только
последний старт текущего boot: старт без `track_ended` в завершившемся boot или
перед более поздним стартом MUST закрываться как `session_lost` с `playedMs` и
позицией из последнего `track_progress`.

#### Scenario: Первый отчёт по старой истории

- **WHEN** отчёт открывается впервые после обновления, а за день есть только
  события
- **THEN** приложение строит факты, показывает отчёт и сохраняет кэш дня

#### Scenario: Повторный отчёт

- **WHEN** отчёт открывается снова при неизменном журнале
- **THEN** повторного разбора нет, используются факты из кэша

#### Scenario: Изменился журнал или builder

- **WHEN** размер или время журнала изменились либо сменилась версия builder'а
- **THEN** кэш дня пересобирается

#### Scenario: Непроверенные часы

- **WHEN** факт построен по событиям с `clockVerified=false`
- **THEN** факт помечен `clockVerified=false` и не расширяет период отчёта
  в прошлое

#### Scenario: Старт без окончания в старом boot

- **WHEN** в журнале есть `track_started` без `track_ended`, а позже начался
  другой трек или загрузился новый boot
- **THEN** факт закрывается как `session_lost` с последней позицией и
  `playedMs`, а открытым остаётся только текущее прослушивание

#### Scenario: Текущий трек ещё играет

- **WHEN** у последнего старта текущего boot нет окончания
- **THEN** факт остаётся открытым и в итоги отчёта не входит

### Requirement: Слияние фактов

`PlaySource` MUST объединять live и history. Live MUST иметь приоритет. Для
дня с обоими источниками history MUST строиться только до `liveSince`, а
пересекающиеся записи MUST отбрасываться. Дубликаты `playId` MUST
схлопываться. Дубликаты одного прослушивания MUST схлопываться и по
натуральному ключу `trackKey`+`startedAt`, даже если `playId` разные: остаётся
live-запись, затем закрытая, затем не-restored, затем запись с более ранним
`endedAt`. Порядок MUST быть детерминированным: по `startedAt`, затем `playId`.

#### Scenario: Обновление в середине дня

- **WHEN** приложение обновилось, и после этого в тот же день появились
  live-факты
- **THEN** отчёт показывает live-факты и history только до `liveSince`

#### Scenario: Один и тот же факт из двух источников

- **WHEN** live и history содержат запись с одинаковым `playId`
- **THEN** в отчёте остаётся одна live-запись

#### Scenario: Пересечение интервалов

- **WHEN** history-запись пересекается с live-записью по времени и треку
- **THEN** history-запись отбрасывается, а диагностика показывает
  предупреждение

#### Scenario: Одно прослушивание закрыто дважды

- **WHEN** history содержит два факта с одним `trackKey` и `startedAt`, но
  разными `playId`
- **THEN** в отчёте остаётся один факт, а диагностика показывает схлопнутый
  дубль

#### Scenario: Открытая и закрытая запись одного прослушивания

- **WHEN** одно прослушивание есть и открытым (старт без окончания), и закрытым
  (окончание записалось позже, в следующем дне)
- **THEN** в отчёте остаётся закрытая запись, а открытых прослушиваний не
  остаётся
