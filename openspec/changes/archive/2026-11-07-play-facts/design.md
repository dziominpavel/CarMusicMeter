# Design

## Context

- `ListeningTracker.endEvent` уже собирает все поля прослушивания:
  `playedMs`, `rawPlayedMs`, `endReason`, `startedAt`, `volumeStats`,
  `restored`. Факт можно не считать заново, а отобразить из этого события.
- `EventLog.appendAll` пишет пачку в один файл и вызывает `fsync`;
  `exportTo` копирует файлы и считает SHA-256 по ходу.
- `OpenPlay` уже переживает перезапуск процесса и хранит `startedAt`,
  `playedMs` и громкость.
- `scripts/report.py` содержит эталонную логику `analyze()`: порядок по
  `bootId`/`monoMs`, поправка `clock_changed`, склейка, `endReason`.
- Магнитола слабая, adb нет, журнал append-only с fsync, сеть недоступна.

## Goals / Non-Goals

**Goals:**

- Одно прослушивание — ровно один факт, с стабильным `playId`.
- Факт не теряется и не дублируется при перезапуске и сбое записи.
- История до обновления разбирается один раз и кэшируется.
- ZIP содержит готовые факты, пригодные для отчёта, ПК и ИИ.
- `report.py` остаётся эталоном и читает новые факты.

**Non-Goals:**

- Room, индекс коллекции, UI отчёта — следующий change.
- Сеть, AI, `INTERNET`.
- Переразбор старых ZIP на ПК: только fallback по событиям.
- Изменение семантики захвата и существующих событий.

## Decisions

### D1. Live-факт — отображение `track_ended`

Трекер не считает факт второй раз: `PlayRecord.from(trackEnded, ...)` берёт
готовые поля события. В `Active` и `OpenPlay` добавляется `playId`,
который рождается в `start()` и переживает восстановление. Счётчики
`seekBack`/`seekForward` добавляются в `Active` при обработке перемотки;
builder считает их по событиям `seek`.

Почему не отдельный пересчёт: трекер уже знает `playedMs` и `volumeStats`,
повторный расчёт дал бы второй источник истины. Почему факт не заменяет
событие: событие остаётся аудитом и диагностикой, факт — стабильным
контрактом. Дублирование ~400 байт на прослушивание приемлемо.

### D2. Закрытие, fsync и восстановление

`EventLog.appendClose(event, play)` пишет событие в `events-*.jsonl`,
вызывает `fsync`, затем пишет факт в `plays-*.jsonl` и снова `fsync`;
checkpoint очищается после обеих записей. Между двумя файлами нет атомарной
транзакции, поэтому восстановление строится на идентичности:

- событие есть, факта нет → builder восстанавливает факт по `bootId` +
  `startedAt` + `trackKey`;
- факт есть, события нет → факт остаётся единственным;
- оба есть → live-факт приоритетнее, дубль по `playId` схлопывается.

Почему не один общий файл: диагностический журнал и контракт фактов должны
меняться независимо. Почему не WAL: объём и сложность не оправданы, потеря
одного факта восстанавливается из события.

### D3. Builder истории — порт `analyze()`

`PlayBuilder` читает `events-YYYY-MM-DD.jsonl`, упорядочивает события по
исправленному `ts`, внутри `bootId` — по `monoMs`, применяет
`clock_changed.wallDelta` (как `report.py`), склеивает
`track_started`/`track_progress`/`track_ended`, берёт `endReason` и `playedMs`
из события. Результат помечается `origin=history`, `clockVerified` берётся из
событий. Builder запускается лениво для выбранного периода отчёта и для
полного экспорта; пользователь ничего не нажимает.

Почему порт, а не вызов Python: магнитола не запускает Python, а отчёт должен
работать без ПК. Почему один раз: повторный разбор сотен тысяч событий на
каждом открытии не нужен. Цена — порт `analyze()` и parity-тесты.

### D4. Кэш — JSONL по дням, без Room

`files/report/cache/v1/plays-YYYY-MM-DD.jsonl` с первой строкой-мета:
`builderVersion`, имя источника, размер, mtime. Файл пишется во временный и
переименовывается. Инвалидация — по версии builder'а или изменению источника.
Кэш удаляется вместе с днём и может быть удалён вручную — тогда факты
пересоберутся.

Почему не Room: за год порядка 10 тысяч фактов, парсинг занимает секунды;
файлы видны в ZIP и диагностике, не требуют миграций. Room появится, когда
понадобятся сложные запросы и индекс коллекции.

### D5. Слияние и watermark

В `Prefs` хранится `liveSince` — время первого live-факта. `PlaySource`
для каждого дня:

1. берёт все live-факты;
2. если день пересекает `liveSince`, добавляет history только до него;
3. отбрасывает history, пересекающуюся с live по интервалу и `trackKey`;
4. схлопывает дубликаты по `playId`;
5. сортирует по `startedAt`, затем `playId`.

Открытый факт читается отдельно из `open.json`/`LiveState` и в список
закрытых не попадает. Непроверенные факты помечаются и в основной период не
подмешиваются.

### D6. Экспорт: сгенерированные записи

`EventLog.exportTo` получает `generated: List<ExportEntry>` с путём и
поставщиком байтов. Для фактов это:

- `plays/plays.jsonl` — слитые факты за диапазон;
- `plays/plays.csv` — те же факты для Excel (UTF-8 BOM, CRLF);
- `DATA_DICTIONARY.csv` — описание полей;
- `SCHEMA.md` — глоссарий, enum'ы, null, версии.

Байты хешируются при записи в ZIP так же, как у файлов. `manifest.json`
получает `playsSchemaVersion` и блок `plays`; `schemaVersion` остаётся 2,
потому что новые поля аддитивны и старые потребители их игнорируют.

Почему не хранить готовые CSV на диске: они зависят от диапазона и дублируют
факты. Почему не генерировать в памяти всё: для года это единицы мегабайт,
приемлемо; при росте — поток во временный файл.

### D7. Хранение и очистка

`trimOld` удаляет вместе с днём `plays-<day>.jsonl` и кэш этого дня.
Непроверенный журнал и его факты не удаляются по сроку. Кэш не считается
источником и не попадает в ZIP. `storageStats` учитывает plays и кэш в общем
объёме.

### D8. Совместимость с `report.py`

`report.py` сначала ищет `plays/plays.jsonl`; если его нет — читает
события старым путём. Опция `--plays FILE` выводит реконструированные
прослушивания для parity-теста. Сравнение: число фактов, `playId`,
`endReason`, `playedMs` — точно; `startedAt`/`endedAt` — с допуском 1 с.

### D9. Диагностика

Экран диагностики показывает: число live/history фактов, дни кэша, версию
builder'а, время последнего разбора, открытый факт, пересечения, битые строки,
ошибки записи факта. Ошибка разбора не роняет отчёт.

## Data model

| Поле | Тип | Источник |
|---|---|---|
| `playsSchemaVersion` | int | константа 1 |
| `playId` | string | UUID на старте, переживает restore |
| `origin` | `live`/`history` | писатель |
| `bootId` | string | конверт процесса |
| `trackKey` | string | трекер |
| `package`, `source` | string/null | трекер |
| `title`, `artist`, `album` | string/null | трекер |
| `durationMs` | long/null | трекер |
| `startedAt`, `endedAt` | epoch ms | трекер, поправка часов |
| `playedMs`, `rawPlayedMs` | long | трекер |
| `endPositionMs` | long/null | трекер |
| `endReason`, `completed` | string/bool | трекер |
| `restored`, `clockVerified` | bool | трекер/конверт |
| `volumeStart/End/Low/High/Max` | int/null | трекер |
| `volumeSource`, `volumeStats` | string/object | трекер |
| `seekBack`, `seekForward` | int | трекер/builder |
| `deviceId`, `appVersion` | string | писатель |

## Flow

```
track_ended ──► PlayRecord (live) ──► plays-YYYY-MM-DD.jsonl
events-*.jsonl ──► PlayBuilder ──► cache/v1/plays-YYYY-MM-DD.jsonl
                         │
                         ▼
                    PlaySource ──► export (plays.jsonl/csv, manifest)
```

## Failure modes

- **Сбой между записями** → builder восстанавливает факт по событию; дубля нет.
- **Битая строка** → пропуск, счётчик в диагностике.
- **Устаревший кэш** → пересборка по версии/источнику.
- **Пересечение live/history** → history отбрасывается, предупреждение.
- **Непроверенные часы** → `clockVerified=false`, отдельный учёт.
- **Нет места** → ошибка записи, существующий backoff захвата, факт не теряется
  молча.
- **Удалён кэш** → пересборка из журнала.

## Compatibility

| Источник | Поведение |
|---|---|
| Старый ZIP без `plays` | `report.py` читает события, как раньше |
| Новый ZIP с `plays` | новый `report.py` читает факты |
| Новый ZIP, старый `report.py` | незнакомые файлы игнорируются |
| Обновление в середине дня | live + history до `liveSince` |
| Приложение без фактов | builder строит историю |

## Testing

- JVM: сериализация `PlayRecord`, `PlayBuilder`, `PlayCache`, `PlaySource`,
  `trimOld`, `ExportManifest`.
- Golden: мини-архив (3 прослушивания, open, restored, unverified) и
  ожидаемый `plays.jsonl`.
- Parity: `report.py --plays` против builder'а на реальных архивах
  `data/exports`.
- Устройство: выгрузка, открытый трек, замена APK в середине, выключение
  питания.
- Регрессия: существующие тесты захвата и экспорта.

## Trade-offs

- Факт дублирует поля события — плата за стабильный контракт и быстрый отчёт.
- Builder — порт `analyze()`; риск расхождений закрывается parity-тестом.
- Нет Room — быстрее стартовать, но сложные запросы появятся позже.
- Нет атомарной транзакции между файлами — восстановление вместо WAL.
