# Design

## Context

См. `proposal.md` — Why. Сейчас весь экран собран в одном `ProbeScreen.kt`
(883 строки) и одном вертикальном свитке; `MainActivity` держит состояние,
настройки и диалоги. Навигационной библиотеки нет, зависимостей добавлять не
хочется. `isTeyesUnit` вычисляется внутри `MediaWatchService` и наружу не
отдаётся. `CaptureHealthCard` смотрит только на `captureError`, поэтому после
остановки службы может показывать «идёт».

Ограничения: один модуль `:app`, Compose Material 3, minSdk 29, тёмная тема,
телефон для 90% проверок и ландшафтная магнитола Teyes CC3 как целевой экран.
adb на магнитоле нет.

## Goals / Non-Goals

**Goals:**

- Три экрана с разными задачами: пульт, диагностика, настройки.
- Одна вычисляемая модель статуса сбора, пригодная для JVM-тестов.
- Главный экран, который на широком ландшафте показывает статус, трек и
  действия без прокрутки.
- Сохранить все текущие действия и настройки, убрав их с главного экрана.

**Non-Goals:**

- Не менять поведение захвата, записи, громкости, хранения и экспорта.
- Не добавлять Navigation Compose, DI, новые permissions и сеть.
- Не делать экран статистики v2 и не вводить bottom navigation «на будущее».
- Не переделывать диалоги экспорта и подтверждения удаления.

## Decisions

### 1. Три пункта назначения без Navigation Compose

`MainActivity` хранит `AppScreen` (`DASHBOARD`, `DIAGNOSTICS`, `SETTINGS`) в
`rememberSaveable`; `BackHandler` возвращает на главный экран. Диалоги остаются
в `MainActivity`, потому что они уже владеют экспортом и подтверждением
удаления.

Альтернативы: bottom tabs — лишняя навигационная полоса и лишний тап на
маленькой высоте магнитолы; Navigation Compose — новая зависимость ради трёх
экранов; один свиток — это текущая проблема. Ручное состояние выигрывает по
простоте; если в v2 появится статистика, тогда и будет повод для нормальной
навигации.

### 2. Чистая модель статуса в `data`, а не в composable

Новый `CaptureStatus` — обычный Kotlin-объект без Android:

```
enum CaptureStatus { RECORDING, DEGRADED, NOT_RECORDING, ERROR }
enum CaptureAction { START_SERVICE, OPEN_NOTIFICATION_SETTINGS, OPEN_DIAGNOSTICS, NONE }
data class CaptureStatusView(status, headline, detail, lastSuccessAt, action)
```

`deriveCaptureStatus(state: LiveState, nowMs: Long): CaptureStatusView`
вычисляет состояние по приоритету:

```
1. служба не запущена                         -> NOT_RECORDING (Запустить)
2. captureError != null                       -> ERROR (Диагностика)
3. успешного тика ещё не было                 -> NOT_RECORDING (запускается)
4. последний тик старше 10 секунд             -> NOT_RECORDING (нет свежих данных)
5. droppedEvents > 0                          -> DEGRADED (потери)
6. музыка играет, источника нет и нет доступа -> DEGRADED (Разрешить)
7. музыка играет, источника нет               -> DEGRADED (Диагностика)
8. иначе                                      -> RECORDING
```

Порог 10 секунд выбран с запасом к интервалу опроса 0.5–1 с и backoff до 10 с;
ошибка имеет приоритет, поэтому во время backoff показывается «ошибка», а не
ложное «не идёт». `droppedEvents` накапливается за запуск службы и после
восстановления не сбрасывается: для v0 это осознанно — потеря данных важнее
зелёного статуса; счётчик и последняя ошибка видны в диагностике.

Главный экран обновляет `nowMs` раз в секунду через `produceState`, пока
находится в композиции. Без этого статус «устарел» не пересчитается, если
служба перестала присылать обновления.

Альтернатива: вычислять статус внутри `DashboardScreen` — нельзя тестировать
JVM-тестами и легко снова получить расхождение между карточками. Альтернатива:
добавить статус в `LiveState` — тогда его придётся пересчитывать по таймеру в
службе и хранить производное состояние.

### 3. Признак Teyes-устройства и источники

`DeviceProfile.isTeyes(manufacturer, model)` выносится из
`MediaWatchService` в `data`, чтобы UI и служба не расходились. В `LiveState`
добавляется `teyesDevice`, `ListeningRepository.setTeyesDevice(...)`;
`CarMusicMeterApp.onCreate` и служба выставляют его при старте. Для устойчивости
к клонам прошивки UI также считает Teyes-источники применимыми, если уже есть
`stockSource`, `fytMetadataReceived` или `teyesAvailable`.

На телефоне скрываются строки «Штатный плеер», FYT, лаунчера, accessibility и
MCU; остаются MediaSession, уведомления и громкость Android. В диагностике
неприменимые источники не показываются, а не помечаются тревожным «нет данных».

### 4. Разделение экранов и компонентов

`ProbeScreen.kt` разбирается на:

- `DashboardScreen.kt` — шапка, статус, алерт, «Сейчас играет», действия,
  строка «Сегодня», вход в диагностику.
- `DiagnosticsScreen.kt` — секции «Сбор», «Источники», «Текущая сессия»,
  «Последние события»; там же кнопки запуска/остановки службы.
- `SettingsScreen.kt` — чек-лист готовности, хранение и срок хранения, помощь,
  версия и дата сборки.
- `ui/AppComponents.kt` — общие `StatusChip`, `StatusBanner`, `SettingsRow`,
  `SectionHeader`, `KeyValueRow`.

`LiveCard` переиспользуется как основа `NowPlayingCard`, но из неё убираются
`packageName`, число ключей метаданных, сырой `state.error` и дублирующая
строка громкости. Громкость и источник показываются один раз — в карточке
трека. `RecentEventsCard` и `EventRow` переезжают в диагностику.

Строка «Сегодня» показывает только события и треки. `sessionsSeen` переезжает
в диагностику как «смен пакета», потому что это не число сеансов прослушивания.

### 5. Раскладка главного экрана

Портрет/узкий экран: одна колонка с вертикальной прокруткой, порядок
«статус → трек → действия → сегодня → диагностика».

Широкий ландшафт (`maxWidth >= 840.dp` и `maxHeight >= 480.dp`): шапка на всю
ширину, ниже две колонки. Слева — трек и действия, справа — «Сегодня» и вход в
диагностику. Статус и алерт остаются в шапке. Если высоты не хватает, экран
откатывается к одной колонке со скроллом, чтобы ничего не обрезалось.

Альтернатива: просто ограничить ширину карточек — уменьшит растянутость, но
не уберёт прокрутку и не использует площадь магнитолы.

### 6. Настройки и готовность

Чек-лист: доступ к уведомлениям, батарея, автозапуск — обязательные; чтение
интерфейса — необязательное и только на Teyes. Если обязательные пункты
выполнены, показывается «Готово к машине», а accessibility не красится в
предупреждение.

Срок хранения остаётся четырьмя пресетами, но внутри настроек; используется
существующий поток подтверждения удаления из `MainActivity`. Период экспорта
живёт только в `ExportDialog`. Объём журнала и снимков показывается в
настройках, а не на главном. «Проверка в машине» — раскрывающаяся секция
настроек, без отдельного экрана и без чтения файлов из `docs/` во время работы.

### 7. Читаемость и акценты

На главном вторичный текст (источник, громкость, время обновления) использует
`bodyMedium` 14sp; `labelSmall` 11sp остаётся для диагностики. Интерактивные
строки настроек — не ниже 48dp, основные кнопки — 56dp. Статус всегда имеет
текстовую подпись, цвет — только дополнение. «Экспорт логов» — filled-кнопка,
«Снять срез» — outlined.

## Risks / Trade-offs

- **Диагностика спрятана за один тап, а в v0 она нужна в машине** → статус-чип,
  строка источника в треке, алерт при проблеме и один тап до полной таблицы.
- **Счётчик потерь не сбрасывается после восстановления** → статус остаётся
  «идёт с замечаниями» до перезапуска службы; для пробника это честнее, чем
  скрывать потерю. В диагностике видны число потерь и последняя ошибка.
- **Ручная навигация и back** → `rememberSaveable` и `BackHandler`; проверить
  поворот экрана и возврат из настроек.
- **Две колонки могут не влезть при крупном шрифте** → порог по ширине и высоте,
  fallback в одну колонку, проверка с font scale 1.3.
- **Эвристика Teyes может ошибиться на клоне** → показывать источники также по
  фактическим данным (`stockSource`, `fytMetadataReceived`, `teyesAvailable`).
- **Настройки стали менее заметными** → шестерёнка в шапке, чек-лист
  готовности и алерт, если обязательный доступ не выдан.
- **`lastSuccessAt` хранится по настенным часам** → скачок времени может на
  секунду дать ложное «нет свежих данных»; следующий тик это исправляет.

## Migration Plan

Миграции данных нет: `Prefs`, журнал и экспорт не меняются. После обновления
APK настройки остаются на месте, меняется только их расположение. Откат —
возврат UI-коммита; служба и формат журнала не затронуты. `README.md` и
`docs/HEADUNIT_TEST.md` обновляются вместе с экранами, чтобы пути к настройкам
не разошлись с реальностью.
