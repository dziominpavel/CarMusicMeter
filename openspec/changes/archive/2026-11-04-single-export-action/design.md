# Design

## Context

См. `proposal.md` — Why. Технический контекст, который определяет решения:

- Диалог экспорта уже считает план асинхронно при открытии
  (`LaunchedEffect(showExportDialog, exportRange)` → `planExport`), а сам ZIP
  собирается позже, после SAF.
- `SnapshotWriter.capture` синхронный, работает на IO-диспетчере и уже
  вызывается службой на каждом `track_started` — то есть цена вызова известна
  и приемлема для магнитолы.
- `ExportPlanner` фильтрует файлы по дате из имени; снимок получает имя
  `snapshot-<дата>-<время>-<reason>.json`, поэтому попадает в любой период.
- План и манифест менять не нужно: ZIP по-прежнему содержит `logs/`,
  `snapshots/`, `crashes/` и `manifest.json`.

## Goals / Non-Goals

**Goals:**

- Одно действие на главном экране; свежий снимок всегда в архиве.
- Счётчик в диалоге честно отражает содержимое ZIP.
- Экспорт не ломается из-за сбоя снимка.

**Non-Goals:**

- Не менять формат ZIP, манифеста и имена файлов.
- Не трогать автозапись снимка на `track_started`.
- Не добавлять экран просмотра снимков внутри приложения.

## Decisions

**1. Снимок снимается при открытии диалога, а не при подтверждении.**
Альтернатива — снимать при «Экспортировать»: тогда план пришлось бы пересчитывать
после SAF, а число файлов в диалоге разошлось бы с архивом. Плата — снимок
остаётся на диске, если пользователь закрыл диалог. Это дешевле, чем расхождение
счётчика, и укладывается в лимит 600 снимков.

**2. Снимок встраивается в тот же IO-блок, что и планирование.** Порядок
«capture → planExport» гарантирует, что новый файл уже на диске и попал в план.

**3. Причина снимка — `export`.** `manual` больше не используется: на ПК по
имени файла видно, что снимок сделан при выгрузке. Шаблон имени не меняется,
`scripts/report.py` причину не разбирает.

**4. Сбой снимка не прерывает экспорт.** `runCatching` вокруг `capture`,
ошибка уходит в `CrashLogger`, план строится по тому, что есть. Иначе сломанный
пробник лишил бы пользователя возможности выгрузить журнал.

**5. Разбивка плана по видам считается из `ExportPlan.files`.** Диалог получает
счётчики `logs`/`snapshots`/`crashes` рядом с общим объёмом; отдельного поля
в модели не нужно, вид файла уже есть у `StoredFile.kind`.

**6. `takeSnapshot()` удаляется целиком**, `SnapshotWriter` остаётся публичным
для службы и экспорта — второй точки входа для снимка нет.

**7. Тексты.** Инструкция «Проверка в машине», `README` и `HEADUNIT_TEST`
теряют шаг «снять срез»; в диалоге появляется строка, что свежий снимок уже снят.

## Risks / Trade-offs

- **Лишний файл при отмене диалога** → лимит 600 снимков и чистка по количеству
  уже покрывают это; удалять файл при отмене не будем, чтобы не рисковать
  удалением не того файла.
- **`coverage` архива расширяется до сегодняшнего дня**, даже если журнал
  кончился раньше → это правда: в архиве есть снимок за сегодня.
- **Ветка «нет данных за период» становится почти недостижимой** → остаётся
  аварийным путём на случай сбоя снимка, проверка `plan.isEmpty` сохраняется.
- **Стоимость снимка на магнитоле** (обход сессий, уведомлений, окон) → это
  единицы килобайт и уже происходит на каждом старте трека; диалог открывается
  редко.
- **Пользователь, привыкший к двум кнопкам** → подсказка в диалоге объясняет,
  что снимок уже внутри.

## Open Questions

- Переименовывать ли кнопку «Экспорт логов» в «Выгрузить диагностику»: в архиве
  не только логи. Решение не влияет на спеки и задачи; по умолчанию оставляем
  текущую подпись.
