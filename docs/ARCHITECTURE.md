# Архитектура CarMusicMeter

## Ограничения, из которых всё выросло

1. **Магнитола Teyes CC3, Android 10.** Коллекция ~3000 треков на USB, рядом копия на ПК.
2. **Штатный плеер остаётся.** Он выведен на виджет и главный экран, удобен в разделённом
   экране; своё приложение не должно его подменять.
3. **adb на магнитоле недоступен.** APK ставится с флешки, логи забираются ZIP-архивом.
4. **Питание выключается вместе с зажиганием.** Незаписанные в файл события теряются.
5. **На магнитоле нельзя считать аудиопризнаки.** Индекс библиотеки и отчёты — на ПК.

Отсюда два принципа: приложение только **наблюдает** и пишет **маленькие события**,
а вся тяжёлая работа уезжает на компьютер.

## Компоненты

| Компонент | Ответственность |
|---|---|
| `MediaWatchService` | foreground-служба: цикл опроса, запись событий, уведомление |
| `NotificationWatchService` | доступ к уведомлениям; текст медиа-уведомлений как резервный источник |
| `MediaSessionProbe` | чтение `MediaSessionManager`, снимок сессии, полный JSON-дамп |
| `StockPlayerBridge` | последнее состояние штатного плеера Teyes вне MediaSession |
| `StockPlayerAccessibilityService` | чтение видимых окон плеера, split-screen, debounce и диагностика UI |
| `TeyesToolkitClient` | binder-клиент `com.syu.ms`, реальная громкость MCU |
| `SourcePicker` | выбор источника «сейчас играет»: MediaSession или штатный плеер |
| `ListeningTracker` | чистая логика: границы трека, пропуск, пауза, перемотка |
| `EventLog` | JSONL с fsync, снимки, ZIP-экспорт |
| `ListeningRepository` | `StateFlow` для экрана, счётчики за день |
| `SnapshotWriter` | окружение, громкость, аудиовыходы, все сессии, уведомления, `stockPlayer`, `stockPlayerUi`, `teyes`, пакеты |
| `AutostartScheduler` / `AutostartJobService` | persisted JobScheduler и страховка автозапуска |
| `AutostartActivity` | невидимый пункт для списка автозапуска Teyes |
| `DashboardScreen` / `DiagnosticsScreen` / `SettingsScreen` | главный пульт, диагностика и настройки |

## Поток данных

```
MediaSessionManager ──► MediaSessionProbe ─┐
titlesReceiver ───────► StockPlayerBridge ─┼─► SourcePicker ─► ListeningTracker
accessibility ─► окна/debounce ► StockPlayerBridge ─┤                 │
уведомление ──────────► StockPlayerBridge ──────────┘                 ▼
NotificationListener ─► NotificationCache ─────────────────► EventLog (JSONL)
Teyes MCU ────────────► TeyesToolkitClient ─┐                       │
AudioManager ───────────────────────────────┴─► VolumeSelector      │
                                                        «Экспорт логов» (SAF)
                                                                  ▼
                                                              ZIP на флешку
```

### Цикл службы

- каждые **500 мс** читается громкость: сначала MCU Teyes, иначе `STREAM_MUSIC`;
- каждые **1000 мс** запрашиваются активные сессии и последнее состояние штатного плеера;
- раз в **5 с** MCU перечитывается, если вендорный callback молчит;
- при играющем треке цикл идёт раз в 500 мс, в простое — раз в 1000 мс;
- каждое изменение превращается в событие и сразу пишется на диск.

Частота выбрана так, чтобы не крутить binder-вызовы без нужды, но поймать
переключение трека и поворот ручки громкости.

Длительности, позиция и grace-интервалы считаются по `SystemClock.elapsedRealtime()`;
`System.currentTimeMillis()` используется только для `ts` событий. Скачок
настенных часов поэтому не меняет `playedMs` и не рвёт трек.

Ошибка одного тика (например, `IOException` при записи) не завершает цикл:
служба делает backoff, пишет `capture_error`, показывает состояние сбора на
экране и в уведомлении и продолжает после восстановления. Полный список
потерь — в `LiveState.droppedEvents`.

Остановка службы сначала отменяет цикл и ждёт его завершения, затем один раз
финализирует текущий трек. Если цикл не завершился за 2 секунды, финализация
пропускается, чтобы не записать `track_ended` параллельно с тиком; причина
попадает в health-диагностику.

## События

Все события — строки JSONL в `files/logs/events-YYYY-MM-DD.jsonl`.
Общие поля: `ts` (epoch ms), `type`, `bootId`, `monoMs`.

`bootId` — короткий идентификатор процесса, `monoMs` — `elapsedRealtime()` на
момент записи пачки. Оба ставит `EventLog`, а не построители событий. Конверт
нужен, чтобы отчёт мог упорядочить события и поправить даты, если часы
магнитолы сбились: поправка выводится из событий `clock_changed`
(`wallDelta` + `monoMs`) того же `bootId`, отдельного поля не требуется.
Старые ZIP без конверта отчёт читает по `ts`, как раньше.

| Тип | Когда | Ключевые поля |
|---|---|---|
| `track_started` | появился новый трек | `trackKey`, `package`, `source`, `title`, `artist`, `album`, `mediaId`, `durationMs`, `positionMs`, `volume`, `volumeMax`, `volumeSource`, `actions`, `metadataKeys` |
| `track_progress` | раз в 60 с и на паузе/остановке | `trackKey`, `positionMs`, `playedMs`, `durationMs`, `volume`, `volumeMax`, `volumeSource`, `phase` |
| `track_ended` | трек сменился/пропал/служба остановилась | `playedMs`, `endPositionMs`, `endReason`, `completed`, `volumeStats`, `volumeStart/End/Low/High`, `volumeChanges`, `volumeSource`, `nextTitle` |
| `capture_error` | ошибка тика или записи | `stage`, `message`, `exception`, `consecutive`, `droppedEvents` |
| `capture_recovered` | цикл восстановился после ошибки | `failures`, `lastError` |
| `clock_changed` | настенные часы прыгнули относительно монотонных | `wallDelta`, `monoDelta`, `driftMs` |
| `playback_paused` / `playback_resumed` / `playback_stopped` | смена состояния | `trackKey`, `source`, `positionMs`, `playedMs` |
| `seek` | позиция скакнула больше чем на 5 с | `fromMs`, `toMs`, `deltaMs` |
| `volume_changed` | изменилась абсолютная громкость | `previous`, `value`, `max`, `delta`, `level`, `source` (`mcu`/`audio`), `sourceReason`, `muted`, `trackKey` |
| `volume_source_changed` | сменился источник громкости | `from`, `to`, `fromValue`, `toValue`, `fromMax`, `toMax`, `sourceReason`, `trackKey` |
| `mute_changed` | включили/выключили mute | `muted`, `volume`, `volumeMax`, `source`, `sourceReason`, `trackKey` |
| `notification` | уведомление | `package`, `title`, `text`, `bigText`, `actions`, `hasMediaSession`, `mediaLike`, `extras`, `remoteTexts` |
| `stock_player_text` | изменились название, исполнитель, альбом или набор сырых строк (позиция не считается) | `package`, `title`, `artist`, `source`, `playing`, `rawTexts` |
| `stock_player_ui` | изменилась структура окна плеера (тикающая позиция и `rangeInfo.current` не считаются); дополнительно раз в 5 минут | `package`, `allTexts`, `nodes`, `windows`, `accepted`, `rejectReason`, `confidence`, `rangeInfo` |
| `capture_gap` | окно плеера пропало или вернулось | `active`, `reason`, `lastTitle`, `lastSource`, `isMusicActive`, `windows` |
| `teyes_toolkit` | изменилось состояние MCU-сервиса | `available`, `connected`, `module`, `error` |
| `service_started` | служба запущена | `source` (`manual`, `boot`, `job`, `media_mounted`, `app_open`, `teyes_autostart`, `accessibility`, `notification`, `system_restart`) |
| `app_crash` | необработанное исключение | `message`, `exception`, `file` |
| `boot_received` | получен boot-интент | `action` |
| `service_start_failed` | не удалось стартовать foreground-службу | `error`, `source` |
| `notification_listener_connected/disconnected` | доступ включён/выключен | — |

`endReason`:

- `completed` — позиция дошла до конца трека (допуск 3 с) или проиграно почти вся длительность;
- `skipped` — трек сменился в том же плеере, не дослушан;
- `unknown` — трек сменился, но длительность/позиция неизвестны (accessibility без времени);
- `interrupted` — сессию перехватил другой пакет;
- `stopped` — плеер перешёл в `STOPPED`;
- `not_played` — трек был активен меньше 3 секунд и не дослушан;
- `session_lost` — сессия или окно исчезли дольше чем на 5 с;
- `service_stopped` — службу остановили.

### Подписи диагностики

`stock_player_ui` и `stock_player_text` сравниваются по смысловым подписям.
В подписи окна нет строк времени и `rangeInfo.current`, в подписи текста — нет
позиции и тикающего времени. Без этого событие писалась бы на каждом опросе
видимого окна: в реальной выгрузке 2026-11-04 это дало 271 событие и 92%
объёма журнала за 17 минут поездки. Парсер по-прежнему работает по полной
подписи `AccessibilityWindow.signature()` с позицией: ему нужен каждый тик.

## Идентичность трека

`trackKey` — логический ключ: `package::normalized title::normalized artist`.
Регистр и повторные пробелы нормализуются. Длительность, `mediaId`, путь и
источник в ключ не входят: они могут появиться позже или смениться у того же
трека. Ключ фиксируется при `track_started` и не меняется до `track_ended`.

Поздняя длительность, поздний исполнитель и смена `source` (уведомление →
broadcast → accessibility) обновляют snapshot текущего трека, а не создают
второй `track_started`. `mediaId`/`path` остаются в событиях, чтобы на ПК можно
было различить совпавшие по названию треки.

`report.py` группирует новые события по `trackKey`, а старые выгрузки — по
нормализованным `package + title + artist`; поэтому старый и новый формат
можно смешивать в одном отчёте.

## Штатный плеер Teyes и источники

`com.yf.teyesspotify` не публикует MediaSession, поэтому используются четыре
канала в порядке приоритета:

1. `MediaSession` — основной источник для Яндекс.Музыки и совместимых плееров.
2. `titlesReceiver` — broadcast лаунчера FYT с `title`, `play_artist`,
   `play_album`, `play_path`, `play_state`, `play_total`, `play_cur`.
   Приёмник регистрируется динамически в работающей службе.
3. Accessibility — необязательное чтение видимых окон
   `com.yf.teyesspotify`/`com.syu.music`, включая split-screen. Только чтение,
   без кликов. Парсер принимает трек только по уверенной строке
   `Artist - Title.ext` или `Title.ext` + исполнитель; заголовки папок и строки
   списка игнорируются, переходный UI стабилизируется 800 мс. Если окно отдаёт
   время или `SeekBar.rangeInfo`, заполняются `positionMs`/`durationMs`; иначе
   окончание получает `unknown`, а не ложный `skipped`.
4. Уведомление — extras и текст `RemoteViews`, если плеер их публикует.
   Обновление только времени позиции в `text/subText` не создаёт событие;
   в кэш снимка попадают только медиа-подобные уведомления и уведомления
   штатного плеера, а запись события идёт вне main-потока.

`SourcePicker` выбирает играющий источник; при равенстве приоритет у
MediaSession. Каждый трек помечается `source`, поэтому в отчёте можно
отделить данные MediaSession от данных лаунчера/интерфейса. Трек стартует
только в `PLAYING`: сессия на паузе при запуске службы не создаёт фантомное
прослушивание, а `not_played` отсекает случайные старты короче трёх секунд.

Состояние штатного плеера не считается играющим только потому, что существует
уведомление: для `notification` и broadcast без `play_state` используется
`isMusicActive`. Состояние из broadcast/уведомления на паузе живёт 10 минут,
играющее — 30 минут. Accessibility-состояние поддерживается свежим, пока окно
плеера видимо, даже без смены текста; после потери окна оно истекает за 90 секунд,
и трек закрывается как `session_lost`. Границы разрыва пишутся событием
`capture_gap`, а не маскируются последним треком.

Громкость: `TeyesToolkitClient` подключается к `com.syu.ms/app.ToolkitService`
и читает модуль `sound` (`U_VOL`, `U_MUTE`). Это реальная громкость панели.
На проверенной CC3 шкала 0…43: событие пишет `30/43` и `level=30/43`, а не
`max=null`. Если сервис недоступен, используется `AudioManager`; если
максимум явно отключён, `max`/`level` могут быть `null`. Подставлять 25 от
Android нельзя. Смена источника MCU ↔ audio пишется `volume_source_changed`
с причиной (`mcu_available`, `mcu_unavailable`, `mcu_stale`, `mcu_error`,
`audio_fallback`); ложный `delta` между шкалами не создаётся.

`track_ended.volumeStats` хранит start/low/high/end/max/changes отдельно для
каждого источника, поэтому возврат MCU после audio не стирает прежний диапазон.
Верхнеуровневые `volumeStart/End/Low/High` отражают последний сегмент и оставлены
для совместимости. `teyes_toolkit` пишется только при смене подключения/модуля/
ошибки, а не на каждое значение громкости.

Mute не подменяет абсолютную громкость нулём: `volume_changed` несёт реальное
значение, а включение/выключение mute пишется отдельным `mute_changed`. Поэтому
`volumeLow/High` и `volumeChanges` не искажаются.

## Автозапуск

Слои идут от самого надёжного к страховочному:

- `BOOT_COMPLETED`, `MY_PACKAGE_REPLACED`, `QUICKBOOT_POWERON`, `MEDIA_MOUNTED`;
- persisted `JobScheduler` (`AutostartJobService`) после загрузки;
- `NotificationListenerService`, который система поднимает при уведомлениях;
- открытие приложения (`MainActivity.onResume`);
- невидимая `AutostartActivity` для `Настройки → Общие → Автомат. включ.
  при запуске` и `Настройки → Пользователь → Настройки приложений` Teyes.

Каждый слой пишет `service_started` со своим `source`, поэтому по ZIP видно,
что именно сработало. Whitelist Teyes всё равно может требоваться — это
ограничение прошивки, а не приложения.

## Хранение и экспорт

- `files/logs/` — дневные JSONL-файлы; `files/snapshots/` — JSON-снимки;
  crash-файлы лежат рядом с журналом.
- Снимок содержит `volume` для `STREAM_MUSIC`, `volumes` для всех потоков,
  `isVolumeFixed`, `audioMode`, `isMusicActive`, `stockPlayer`, `stockPlayerUi`,
  `notificationListenerConnected`, `teyes`, `packages` и последние уведомления
  с `mediaLike`.
- `EventLog.trimOld(policy)` при старте (и после смены настроек) удаляет
  завершённые дни старше настроенного срока, а при превышении лимита объёма
  (по умолчанию 500 МБ) — самые старые завершённые дни. Текущий день защищён.
- Снимков остаётся 600 последних, crash-файлов — 50. Факт чистки пишется
  событием `retention_trimmed`. Перед сокращением срока хранения экран
  показывает число и объём удаляемых файлов и просит подтверждение.
- Возраст дневного лога считается по дате из имени (`events-YYYY-MM-DD`), а не
  по `lastModified`: часы магнитолы могут сбиваться. Неразборчивые имена
  автоматически не удаляются.
- Экспорт по умолчанию забирает всю историю; пресеты 90 / 30 / 7 дней
  фильтруют журнал и снимки по датам. В `manifest.json` пишутся `range` и
  `coverage` (фактические даты), размер и SHA-256 каждого файла.
- Если системного диалога сохранения нет (Teyes), ZIP пишется в
  `Downloads/CarMusicMeter` через `MediaStore`, а не роняет приложение.

## Эвристики и их слабые места

- **Пропуск** определяется по смене ключа трека, а не по нажатию кнопки: далеко не все
  плееры выставляют `STATE_SKIPPING_TO_NEXT`. Если плеер не отдаёт позицию, остаётся
  только время звучания — этого достаточно для «короткий/длинный», но не для «ушёл на 90-й секунде».
- **Позиция** может обновляться редко. Трекер сам экстраполирует её по часам и скорости,
  а перемоткой считает только расхождение с обновлённым значением. Это защищает от
  ложных перемоток, но реальную перемотку можно не увидеть, если плеер не отдаёт позицию.
- **Громкость** — слабый сигнал: шум дороги, разговор, звонок. Абсолютное значение
  нельзя трактовать как «нравится»; на ПК его нужно нормировать на LUFS трека.
- **Несколько сессий** (навигация, радио, музыка) разруливаются приоритетом: текущий
  пакет → любой играющий → текущий на паузе. Если плеер создаёт фантомные сессии,
  это будет видно в снимке.
- **Медиа-уведомление** — резервный источник. Оно даёт название и исполнителя, но
  обычно не даёт позицию; метрики «сколько играло» и «что было дальше» сохраняются.
- **Accessibility видит только видимое окно.** В полноэкранном навигаторе плеер
  не читается; `capture_gap` фиксирует разрыв, а не подставляет старый трек.
  Split-screen проверяется через `getWindows()`, но не гарантируется прошивкой.
- **Accessibility без времени/SeekBar** не знает длительность. Такие окончания
  помечаются `unknown` и не входят в `skip_rate`/`completion`; это честнее
  ложного `skipped`.

## Почему JSONL, а не Room

На этапе пробника важнее всего **не потерять данные при выключении питания** и **увидеть
сырые поля плеера**. JSONL с fsync даёт и то и другое: файл читается глазами, легко
уезжает на ПК, не требует схемы и миграций. Room появится в v1, когда события начнут
матчиться с индексом библиотеки и понадобятся запросы.

## Объём данных

Один трек — 2 события (старт/конец) плюс несколько пауз и изменений громкости.
При 30–60 треках в день это единицы килобайт; снимок на каждый трек — ещё ~2 КБ.
Даже за год журнал остаётся меньше десятков мегабайт.

## Индекс библиотеки (следующий этап)

На ПК собирается `library.db`:

- теги: исполнитель, название, альбом, год, жанр, номер трека;
- длительность, путь к файлу, размер;
- **LUFS** (`ffmpeg ebur128`) — чтобы нормировать громкость;
- BPM, тональность, энергия — `essentia`/`librosa`;
- Chromaprint (`fpcalc`) — чтобы склеить FLAC и MP3 одного трека.

Файл кладётся на флешку рядом с музыкой. Приложение матчит метаданные MediaSession
по нормализованным «исполнитель + название + длительность ±3 с». Сырые названия из
пробника станут техзаданием для нормализатора: будет видно, плеер берёт теги или
склеивает имя файла.

Это снимает с магнитолы всю тяжёлую работу: она только пишет события, а отчёты
«любимое/пропущенное/ни разу не игравшее» считаются на ПК.

## Чего приложение не делает

- не воспроизводит музыку и не управляет плеером;
- не запрашивает аудиофокус;
- не меняет громкость;
- не ходит в сеть (нет разрешения `INTERNET`);
- не читает файлы коллекции — только метаданные из системы.
