# Архитектура CarMusicMeter

## Ограничения, из которых всё выросло

1. **Магнитола Teyes CC3, Android 10.** Коллекция ~3000 треков на USB, рядом копия на ПК.
2. **Штатный плеер остаётся.** Он выведен на виджет и главный экран, удобен в разделённом
   экране; своё приложение не должно его подменять.
3. **adb на магнитоле недоступен.** APK ставится с флешки, логи забираются ZIP-архивом.
4. **Питание выключается вместе с зажиганием.** Незаписанные в файл события теряются.
5. **На магнитоле нельзя считать аудиопризнаки.** Индекс библиотеки и отчёты — на ПК.

Отсюда два принципа: приложение только **наблюдает** и пишет **маленькие события**,
а вся тяжёлая работа уезжает на компьютер.

## Компоненты

| Компонент | Ответственность |
|---|---|
| `MediaWatchService` | foreground-служба: цикл опроса, запись событий, уведомление |
| `NotificationWatchService` | доступ к уведомлениям; текст медиа-уведомлений как резервный источник |
| `MediaSessionProbe` | чтение `MediaSessionManager`, снимок сессии, полный JSON-дамп |
| `SnapshotPicker` | выбор сессии «сейчас играет» из нескольких активных |
| `ListeningTracker` | чистая логика: границы трека, пропуск, пауза, перемотка |
| `EventLog` | JSONL с fsync, снимки, ZIP-экспорт |
| `ListeningRepository` | `StateFlow` для экрана, счётчики за день |
| `SnapshotWriter` | окружение, громкость, аудиовыходы, все сессии, уведомления |
| `ProbeScreen` | экран диагностики и кнопки |

## Поток данных

```
MediaSessionManager ─┐
                     ├─► MediaSessionProbe ─► SnapshotPicker ─► ListeningTracker
AudioManager ────────┘                                             │
                                                                  ▼
NotificationListener ─► NotificationCache ─────────────────► EventLog (JSONL)
                                                                  │
                                                        «Экспорт логов» (SAF)
                                                                  ▼
                                                              ZIP на флешку
```

### Цикл службы

- каждые **500 мс** читается громкость `STREAM_MUSIC`;
- каждые **1000 мс** запрашиваются активные сессии;
- при играющем треке цикл идёт раз в 500 мс, в простое — раз в 1000 мс;
- каждое изменение превращается в событие и сразу пишется на диск.

Частота выбрана так, чтобы не крутить binder-вызовы без нужды, но поймать
переключение трека и поворот ручки громкости.

## События

Все события — строки JSONL в `files/logs/events-YYYY-MM-DD.jsonl`.
Общие поля: `ts` (epoch ms), `type`.

| Тип | Когда | Ключевые поля |
|---|---|---|
| `track_started` | появился новый трек | `trackKey`, `package`, `title`, `artist`, `album`, `mediaId`, `durationMs`, `positionMs`, `volume`, `actions`, `metadataKeys` |
| `track_ended` | трек сменился/пропал/служба остановилась | `playedMs`, `endPositionMs`, `endReason`, `completed`, `volumeStart/End/Low/High`, `volumeChanges`, `nextTitle` |
| `playback_paused` / `playback_resumed` / `playback_stopped` | смена состояния | `trackKey`, `positionMs`, `playedMs` |
| `seek` | позиция скакнула больше чем на 5 с | `fromMs`, `toMs`, `deltaMs` |
| `volume_changed` | изменилась громкость | `previous`, `value`, `max`, `delta`, `level`, `trackKey` |
| `notification` | медиа-уведомление | `package`, `title`, `text`, `bigText`, `actions`, `hasMediaSession` |
| `app_crash` | необработанное исключение | `message`, `exception`, `file` |
| `boot_received` | получен boot-интент | `action` |
| `service_start_failed` | не удалось стартовать foreground-службу | `error`, `source` |
| `notification_listener_connected/disconnected` | доступ включён/выключен | — |

`endReason`:

- `completed` — позиция дошла до конца трека (допуск 3 с) или проиграно почти вся длительность;
- `skipped` — трек сменился в том же плеере, не дослушан;
- `interrupted` — сессию перехватил другой пакет;
- `stopped` — плеер перешёл в `STOPPED`;
- `session_lost` — сессия исчезла дольше чем на 5 с;
- `service_stopped` — службу остановили.

## Хранение и экспорт

- `files/logs/` — дневные JSONL-файлы; `files/snapshots/` — JSON-снимки;
  crash-файлы лежат рядом с журналом.
- При старте `EventLog.trimOld()` удаляет логи старше **180 дней** и оставляет
  **600 последних снимков**. Отдельного лимита объёма и настройки срока пока нет.
- Экспорт забирает **все текущиеся файлы** журнала и снимков, без фильтра по
  периоду; состав фиксируется в `manifest.json` (размер и SHA-256 каждого файла).
- Очистка сейчас опирается на `lastModified` файла. Для дневных логов надёжнее
  брать дату из имени: часы магнитолы могут сбиваться.
- Планируется: настраиваемый срок хранения, защитный лимит объёма, диапазон
  экспорта (`весь / 90 / 30 / 7 дней`) и поля `range`/`coverage` в манифесте.

## Эвристики и их слабые места

- **Пропуск** определяется по смене ключа трека, а не по нажатию кнопки: далеко не все
  плееры выставляют `STATE_SKIPPING_TO_NEXT`. Если плеер не отдаёт позицию, остаётся
  только время звучания — этого достаточно для «короткий/длинный», но не для «ушёл на 90-й секунде».
- **Позиция** может обновляться редко. Трекер сам экстраполирует её по часам и скорости,
  а перемоткой считает только расхождение с обновлённым значением. Это защищает от
  ложных перемоток, но реальную перемотку можно не увидеть, если плеер не отдаёт позицию.
- **Громкость** — слабый сигнал: шум дороги, разговор, звонок. Абсолютное значение
  нельзя трактовать как «нравится»; на ПК его нужно нормировать на LUFS трека.
- **Несколько сессий** (навигация, радио, музыка) разруливаются приоритетом: текущий
  пакет → любой играющий → текущий на паузе. Если плеер создаёт фантомные сессии,
  это будет видно в снимке.
- **Медиа-уведомление** — резервный источник. Оно даёт название и исполнителя, но
  обычно не даёт позицию; метрики «сколько играло» и «что было дальше» сохраняются.

## Почему JSONL, а не Room

На этапе пробника важнее всего **не потерять данные при выключении питания** и **увидеть
сырые поля плеера**. JSONL с fsync даёт и то и другое: файл читается глазами, легко
уезжает на ПК, не требует схемы и миграций. Room появится в v1, когда события начнут
матчиться с индексом библиотеки и понадобятся запросы.

## Объём данных

Один трек — 2 события (старт/конец) плюс несколько пауз и изменений громкости.
При 30–60 треках в день это единицы килобайт; снимок на каждый трек — ещё ~2 КБ.
Даже за год журнал остаётся меньше десятков мегабайт.

## Индекс библиотеки (следующий этап)

На ПК собирается `library.db`:

- теги: исполнитель, название, альбом, год, жанр, номер трека;
- длительность, путь к файлу, размер;
- **LUFS** (`ffmpeg ebur128`) — чтобы нормировать громкость;
- BPM, тональность, энергия — `essentia`/`librosa`;
- Chromaprint (`fpcalc`) — чтобы склеить FLAC и MP3 одного трека.

Файл кладётся на флешку рядом с музыкой. Приложение матчит метаданные MediaSession
по нормализованным «исполнитель + название + длительность ±3 с». Сырые названия из
пробника станут техзаданием для нормализатора: будет видно, плеер берёт теги или
склеивает имя файла.

Это снимает с магнитолы всю тяжёлую работу: она только пишет события, а отчёты
«любимое/пропущенное/ни разу не игравшее» считаются на ПК.

## Чего приложение не делает

- не воспроизводит музыку и не управляет плеером;
- не запрашивает аудиофокус;
- не меняет громкость;
- не ходит в сеть (нет разрешения `INTERNET`);
- не читает файлы коллекции — только метаданные из системы.
