# TuneMileage — правила для AI-агента

Единый IDE-нейтральный источник always-on правил. Дополнительные правила — в `.cursor/rules/*.mdc`.
OpenSpec-скиллы: `.cursor/skills/`, `.devin/skills/`, `.opencode/skills/`; команды: `.cursor/commands/opsx-*.md`, `.devin/workflows/opsx-*.md`, `.opencode/commands/opsx-*.md`.

## Контекст проекта

Android-приложение на **Kotlin** для сбора статистики прослушиваний в автомобиле.
Работает поверх **штатного плеера** магнитолы Teyes CC3 (Android 10): читает
MediaSession и медиа-уведомления, опрашивает громкость, пишет события в JSONL.
Коллекция (~3000 треков) лежит на USB-флешке и на ПК; анализ и отчёты — на ПК.

Текущий этап — **v0 «пробник»**: выяснить, что отдаёт штатный плеер Teyes,
и собрать первые реальные данные. Это ещё не финальное приложение.

### Стек

- **UI:** Jetpack Compose, Material 3, только тёмная тема (экран в машине)
- **Данные:** append-only JSONL с fsync; Room появится в v1, когда события начнут
  матчиться с индексом библиотеки
- **Архитектура:** один модуль `:app`; `MediaWatchService` (foreground) + `NotificationWatchService`;
  `ListeningTracker` — чистая логика без Android, покрыта JVM-тестами
- **Версия:** файл `version`, меняет только release-скрипт; автобампа нет

### Ключевые пути

- `MainActivity` → `ui/ProbeScreen.kt` — экран диагностики
- `service/MediaWatchService.kt` — цикл опроса, foreground-служба, уведомление
- `service/NotificationWatchService.kt` — доступ к уведомлениям и резервный источник
- `data/ListeningTracker.kt` — старт/конец трека, пропуск, пауза, перемотка
- `data/EventLog.kt` — JSONL, fsync, ZIP-экспорт, снимки
- `probe/MediaSessionProbe.kt` — чтение MediaSession и полный дамп
- `diagnostics/SnapshotWriter.kt` — снимок окружения и всех сессий
- `openspec/specs/` — `playback-capture`, `volume-tracking`, `event-log`

### Железо и ограничения (важно)

- Магнитола **Teyes CC3**, Android 10, коллекция на USB, штатный плеер остаётся:
  он удобен на главном экране и в разделённом экране, свой плеер не планируется.
- **adb на магнитоле недоступен**: не предлагать `adb logcat`, `adb install`,
  `adb shell dumpsys`. Разработка: APK на флешку → установка вручную; логи —
  ZIP через системный диалог сохранения (SAF) на флешку.
- 90% проверок делаются на телефоне. В машину ехать только за тем, что нельзя
  проверить дома (поведение штатного плеера, громкость, автозапуск).
- Штатный плеер может не публиковать MediaSession. Тогда работает резервный
  разбор медиа-уведомлений. Если и его нет — обсуждать accessibility или свой
  плеер, но не ломать текущий сценарий.

## Секреты

- В проекте нет сетевых ключей и токенов; разрешение `INTERNET` не добавлять.
- `local.properties` содержит путь к SDK и пароль релизного keystore; в git не попадает.
- `*.jks` и `*.keystore` — в `.gitignore`.

## Перед изменениями

1. Сверяйся со спеками: `openspec/specs/playback-capture/spec.md`,
   `openspec/specs/volume-tracking/spec.md`, `openspec/specs/event-log/spec.md`.
2. Новые фичи — через OpenSpec change (`/opsx-propose` → review → `/opsx-apply` → `/opsx-archive`).
3. Не меняй `minSdk` без причины: 29 — это Android 10 магнитолы.
4. Не добавляй разрешения «на всякий случай»: уведомления, foreground-служба,
   boot, батарея — и всё.

## Приоритеты при доработках

- **Надёжность записи:** событие либо на диске с fsync, либо его нет. Буферы
  в памяти теряются при выключении зажигания.
- **Не мешать штатному плееру:** никаких запросов аудиофокуса, никакого
  воспроизведения, никаких изменений громкости.
- **Офлайн:** всё локально, без сети и облака.
- **Экран в машине:** крупные кнопки, тёмная тема, читаемость с водительского места.
- **Дешёвый цикл:** нельзя гонять тяжёлый анализ на магнитоле; индекс библиотеки
  и отчёты считаются на ПК.

## OpenSpec (spec-driven development)

Структура: `openspec/` (`specs/`, `changes/`, `changes/archive/`).

### Workflow

- `/opsx-propose <idea>` — создать change с артефактами (proposal.md, design.md, tasks.md, specs/).
- `/opsx-apply` — реализовать задачи из текущего change по спеке.
- `/opsx-archive` — заархивировать завершённый change и обновить основные specs.
- `/opsx-explore` — исследовать кодовую базу перед предложением.

### Когда использовать

- Новые фичи и нетривиальные изменения — через OpenSpec.
- Мелкие правки (опечатка, точечный багфикс) — можно напрямую.
- Артефакты на **русском**, normative keywords — **MUST/SHALL/MUST NOT**.
- Проверка: `openspec validate --all`.

## Версии и changelog (обязательно)

- Версия проекта меняется **только в момент релиза**: бамп вне релиза запрещён,
  между релизами номер остаётся номером последнего релиза.
- В changelog попадают **только глобальные доработки** — новая функция, заметное
  изменение поведения, фикс, который пользователь реально видит. Пункт пишется
  в секцию `## [Unreleased]` в момент работы, а не перед релизом. Мелочь
  (косметика UI, локальные правки, доки, спеки, тесты, CI, рефактор) не пишется.
- Релиз: `release.ps1 -Prepare` → сборка артефактов в `dist/` → `release.ps1`.
- Секция changelog начинается с **пользовательского блока** — жирные метки
  категорий (`**Добавлено**`, `**Исправлено**`) и буллеты, одна строка = одно
  изменение, строка ≤140 символов, без `` ` `` — **выше первой строки** `###`.
  Под категориями идут инженерные детали: change-id, состав, тесты, метрики.
- Заметки GitHub-Release берутся из этого блока автоматически.
- Сверка: `python scripts/check-version.py` (exit 0 — согласовано).
- Полные правила: `docs/versioning.md`.
